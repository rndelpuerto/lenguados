## ADDED Requirements

### Requirement: R-DOCS-MATH2D-SECTION-STRUCTURE

The Docusaurus site SHALL contain a `docs/docs/math2d/` directory organized as a sidebar category with label "math2d" and position 2 (after intro.md at position 1, before contributing at position 3, before the auto-generated API at position 4).

The directory SHALL contain a `_category_.json` file:

```json
{
 "label": "math2d",
 "position": 2,
 "description": "Architecture, design decisions, and reference for @lenguados/math2d",
 "link": {
  "type": "generated-index",
  "description": "In-depth documentation for the @lenguados/math2d package."
 }
}
```

**Rationale:** Docusaurus autogenerated sidebars use `_category_.json` for ordering and labeling. Using the bare package name "math2d" (not `@lenguados/math2d`) follows the convention of Docusaurus category labels being short, human-readable terms. Position 2 places it after the introductory tutorial and before contributor guides.

#### Scenario: Category appears in sidebar

- **WHEN** the Docusaurus sidebar is rendered
- **THEN** "math2d" appears as a collapsible category between "intro" and "Contributing"

#### Scenario: Category has generated index

- **WHEN** a user navigates to the math2d category
- **THEN** they see an auto-generated index page listing all child documents with descriptions

### Requirement: R-DOCS-MATH2D-ARCHITECTURE

The Docusaurus site SHALL contain a `docs/docs/math2d/architecture.md` page that provides the **expanded** architecture documentation, incorporating content from `packages/math2d/docs/architecture/core_principles.md` (translated to English) and serving as the deep-dive complement to the package-level `ARCHITECTURE.md`.

The Docusaurus architecture page SHALL include:

1. Docusaurus frontmatter: `sidebar_position: 1`, `title: "Architecture"`, `description: "Layered architecture, design principles, and key patterns"`
2. Design principles section with the 4 normative axioms (from core_principles.md, **translated to English**)
3. Detailed explanation of each architectural layer with rationale
4. DCE (Dead Code Elimination) policy details and the fdlibm kill-switch strategy (unique content from core_principles.md)
5. Cross-reference to `packages/math2d/ARCHITECTURE.md` as the concise code map

The document SHALL be written entirely in English. The Spanish vision statement from `core_principles.md` MAY be preserved as a blockquote with English translation.

**Relationship to ARCHITECTURE.md files:**

- `packages/math2d/ARCHITECTURE.md` (stays) = concise code map (~100-200 lines, Mermaid diagram, layer descriptions, key patterns, zero-check conventions)
- `docs/docs/math2d/architecture.md` (new) = expanded deep-dive (design principles, axioms, DCE policy, translated core_principles content)
- The package file links to the Docusaurus page for depth; the Docusaurus page links back to the package file for the code map

After this document is created, `packages/math2d/docs/architecture/core_principles.md` SHALL be deleted (its content is now in the Docusaurus page). `packages/math2d/ARCHITECTURE.md` SHALL be KEPT and updated to link to the Docusaurus page.

#### Scenario: Two-level architecture documentation

- **WHEN** a contributor wants to understand the math2d architecture
- **THEN** `packages/math2d/ARCHITECTURE.md` provides the concise code map (layers, diagram, patterns)
- **AND** `docs/docs/math2d/architecture.md` provides the expanded deep-dive (principles, axioms, rationale)

#### Scenario: No duplication of core content

- **WHEN** the package ARCHITECTURE.md and Docusaurus architecture page are compared
- **THEN** the Mermaid diagram and layer descriptions live in the package file
- **AND** the design principles/axioms and DCE policy live in the Docusaurus page
- **AND** they cross-reference each other

#### Scenario: Design principles are present and in English

- **WHEN** a contributor reads the Docusaurus architecture page
- **THEN** they find the 4 normative axioms (Strict Mathematics, Zero-Allocation, Two-Layer Protection, Deterministic Toggle)
- **AND** all axiom descriptions are in English

#### Scenario: core_principles.md content preserved

- **WHEN** the Docusaurus architecture page is compared to the original core_principles.md
- **THEN** all unique content (axioms, DCE policy, kill-switch strategy) is preserved in English

### Requirement: R-DOCS-MATH2D-INTEROPERABILITY

The Docusaurus site SHALL contain a `docs/docs/math2d/interoperability.md` page migrated from `packages/math2d/docs/architecture/module_interoperability.md`.

The document SHALL have frontmatter: `sidebar_position: 2`, `title: "Type Interoperability"`, `description: "Type escalation, rotation drift, and conversion patterns"`.

The document SHALL cover:

- Type escalation gradient (Transform2 → Matrix3 for shear)
- Rotation drift and re-normalization responsibility model
- API facade design (apply vs transform)
- Conversion conventions between types

After migration, `packages/math2d/docs/architecture/module_interoperability.md` SHALL be deleted.

#### Scenario: Interoperability patterns documented

- **WHEN** a contributor needs to understand why Shear requires Matrix3 or how type escalation works
- **THEN** they find the explanation in `docs/docs/math2d/interoperability.md`

#### Scenario: Document has correct Docusaurus frontmatter

- **WHEN** the interoperability page file is inspected
- **THEN** it has `sidebar_position: 2`, `title`, and `description` in YAML frontmatter

### Requirement: R-DOCS-MATH2D-EDGE-CASES

The Docusaurus site SHALL contain a `docs/docs/math2d/edge-cases.md` page migrated from `packages/math2d/docs/research/exhaustive_edge_cases.md`.

The document SHALL have frontmatter: `sidebar_position: 3`, `title: "Edge Cases"`, `description: "IEEE 754 failure modes, normalization paradoxes, and set theory anomalies"`.

The document SHALL catalog IEEE 754 edge cases, normalization paradoxes, and set theory anomalies relevant to the math2d implementation. Content SHALL be in English (translate any Spanish sections).

**Stale content check:** If section 5 (`assertTransform2Like` bug) describes a bug that has been fixed, that section SHALL be removed. If the bug still exists, it SHALL be converted to a GitHub issue and referenced from the document.

After migration, `packages/math2d/docs/research/exhaustive_edge_cases.md` SHALL be deleted.

#### Scenario: Edge case reference accessible

- **WHEN** a contributor encounters unexpected behavior with NaN, Infinity, or zero-length vectors
- **THEN** they find relevant documentation in `docs/docs/math2d/edge-cases.md`

#### Scenario: No stale bug reports in documentation

- **WHEN** the edge cases document is inspected
- **THEN** it does not contain unresolved bug reports that should be GitHub issues

### Requirement: R-DOCS-MATH2D-DESIGN-DECISIONS

The Docusaurus site SHALL contain a `docs/docs/math2d/design-decisions.md` page migrated from `packages/math2d/docs/research/decisions_and_benchmarks.md`.

The document SHALL have frontmatter: `sidebar_position: 4`, `title: "Design Decisions"`, `description: "Architectural decisions, alternatives considered, and industry benchmarks"`.

The document SHALL record architectural decisions preserving: decision statement, context, alternatives considered, rationale, and industry benchmarks (Three.js, Unity, Box2D, gl-matrix). Content SHALL be in English.

Overlapping content with `clean_code_and_solid_application.md` (industry comparisons that appear in both files) SHALL be consolidated — the design-decisions page keeps the benchmarks/comparisons, the design-philosophy page (in contributing/) keeps the SOLID deviations.

After migration, `packages/math2d/docs/research/decisions_and_benchmarks.md` SHALL be deleted.

#### Scenario: Design rationale discoverable

- **WHEN** a contributor asks "why does Rotation2 store (cos, sin) instead of an angle?"
- **THEN** they find the answer with alternatives considered in `docs/docs/math2d/design-decisions.md`

#### Scenario: No duplicate industry comparisons

- **WHEN** the design-decisions page and design-philosophy page are compared
- **THEN** industry benchmark/comparison data appears in only one of them (design-decisions)
